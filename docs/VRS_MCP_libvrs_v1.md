## 1. 정할 것 네 가지 — 결정

**Q1. vrs2 가 libvrs 의 무엇을 쓰나.**
- 쓰는 것: `vrs_open`·`vrs_insert`·`vrs_written`·`vrs_wait`·`vrs_assemble_b`·`vrs_free`·`vrs_close`. 곧 「이 세션 계보의 지금 필요한 입력」을 원문 그대로 받는 기능이다.
- libvrs 의 정의(D1–D11, 시냅스, θ\*, 포크)는 고치지 않는다. 헤르메스 어댑터와 같은 자리, 곧 libvrs 바깥의 어댑터만 새로 짓는다.
- 질의 회수(지금의 memory_context)는 libvrs 에 대응하는 정의가 없다. 그래서 이 G 에 넣지 않는다. 지금 엔진 그대로 두고, K5 는 결함 목록에 「늦춤」으로 남긴다(§3). 없애지 않는다. 질의 회수를 libvrs 정의 위에 다시 세우는 일은 이 G 가 통과한 뒤 별도 L1 이다.

**Q2. 클로드 코드 transcript 형식.**
- 헤르메스 HA1 처럼 어댑터가 transcript 줄을 롤아웃 줄로 바꿔 별도 루트(`~/.claude/vrs/sessions`)에 쓴다. 원본 transcript 는 읽기만 한다.
- 롤아웃 줄의 맨 위 키에 원본 위치 `(transcript 경로, 바이트 위치, 길이, sha256)` 를 둔다. 원본 줄 전체를 다시 싣지 않는다(「연결부만」 결정, 설계 기준 3). payload 에는 libvrs 가 토큰을 재고 조립에 쓸 본문만 둔다.
- 줄 대응(어느 줄이 항목·턴 시작·턴 끝·포크가 되는가, 무엇을 빼는가)은 L1 에서 정의한다.

**Q3. 리눅스 전용 lib 를 Windows 에서.**
- **포팅으로 정한다.** libvrs 에 플랫폼 층 하나(위 리눅스 자리 약 10곳: 파일 보기·대기/깨우기·실제 경로·디렉터리 감시·정지 신호·위치 읽기/쓰기)를 두고, 정의 코드는 한 글자도 바꾸지 않는다. 같은 말뭉치에서 리눅스 lib7 과 바이트로 같은 조립을 내는 것으로 확인한다(M1).
- 원격(home 에서 돌리고 ssh 로 묻기)은 버린다. transcript 원본 2.4 GB 를 다른 기계로 계속 복사해야 해서 「연결부만」 결정에 걸리고, home 이 꺼지면 이 PC 의 기억이 없어진다. 목표 기기(G99)에서도 기억은 기기 안에 있어야 한다.
- WSL 은 버린다. 켜는 일이 시스템 설정 변경이고, `/mnt/c` 에서는 Windows 쪽 쓰기가 inotify 에 안 걸린다.
- **필요한 것: C++20 컴파일러 설치(사용자 승인).** 후보는 winget 의 MinGW-w64 GCC(WinLibs, UCRT)다. 16바이트 CAS(`-mcx16`)와 pthread 를 리눅스 빌드와 같은 꼴로 쓸 수 있다.

**Q4. MCP 도구 집합.**
- 원칙: 질문 하나 = 호출 하나. 스냅숏 id·view 핸들·cursor·release 가 없다. 서버에 요청별 상태가 없다. 페이지는 원본 위치(바이트 범위)로만 나눈다. 응답마다 항목의 원본 위치가 붙는다.
- 도구는 L1 에서 정의한다. 지금 생각하는 꼴은 이렇다(L1 에서 바뀔 수 있다).
  - `session_context`: 이 세션 계보에 대한 libvrs 조립 가운데 기억 몫(현재 입력 밖의 지난 턴), 원문 그대로 + 위치.
  - `read_origin`: transcript·메모리 문서의 위치 범위를 원문 그대로.
  - 옛 질의 회수는 같은 서버에서 옛 이름 그대로 두되, K1·K2 의 땜질 대상이 아니다(늦춤 목록).

## 5. 컴파일러 (KP 닫음, 2026-10-13 11:2x, 사용자 「ㅇㅇ 설치해」)

- **찾은 것(M9 에 닿음):** 이 도구 사슬에서 `std::atomic<16바이트 구조체>` 는 `libatomic` 의 `__atomic_compare_exchange_16` 을 부른다. 그 함수는 `libat_lock_n` → `pthread_mutex_lock` 이다. 곧 **잠금**이다(`is_lock_free() = 0`). 리눅스 libatomic 은 CPU 를 보고 cmpxchg16b 를 고르지만 여기서는 아니다.

  - `rendered` 없음 → 0줄.
- system 줄: `local_command` → developer 메시지(content). 그 밖(compact_boundary·stop_hook_summary·informational·api_error·turn_duration…) → 0줄. 모델 입력이 아니다.
- 메타 줄(queue-operation·mode·custom-title·agent-name·last-prompt·atis-latch·bridge-session·file-history-*·cost-state·summary 와 처음 보는 종류) → 0줄 + 셈.
- 롤아웃 줄의 꼴: `{"timestamp": θ(ℓ), "ordinal": 10자리 고정, "type": "response_item"|"event_msg", "payload": …, "cc": {"o", "n", "k", "h"}}`. `k` 는 ℓ 안의 블록 번호(표지 줄은 `t`·`c`), `h` = sha256(b). payload 의 `id` = `cc1:<o>:<k>`.
- 원본 줄을 다시 싣지 않는다(「연결부만」). payload 에는 libvrs 가 재고 조립할 본문만 있다.

**C3 롤아웃 파일 C(T).** C(T) = 첫 줄 `session_meta`(C4) + T 의 줄을 o 순으로 늘어놓은 각 conv(ℓ) 의 이음이다.
- conv(ℓ) 의 j 번째 줄의 순번 = 1 + Σ_{ℓ′ ∈ T, o′ < o} |conv(ℓ′)| + j, 바이트 위치 = |meta| + Σ_{ℓ′ < ℓ} bytes(conv(ℓ′)) + (앞 j 줄 크기).
- 둘 다 「T 의 줄 집합 위에서 o 로 매긴 합」이다. 처리 순서가 아니다(libvrs D10 의 pos(x) 와 같은 부류).
- 전제 P1c: T 안에서 θ 는 o 순으로 줄지 않는다(코덱스 P1 과 같은 뜻). 깨진 줄은 국소로 알아낼 수 있고 L4 에서 센다.

**C4 계보와 이음 (KC1).**
- 무리 열쇠 g(s): 세션 s 를 돌리는 Claude 프로세스의 pid 파일(그 `sessionId` = s 인 파일)에서, `hostSessionId` 가 있으면 그것(데스크톱 세션), 없으면 `pidDomain:pid:procStart`(CLI 프로세스).
- 사실 집합(만들기 전용, 덮어쓰지 않음):
  - 무리 사실 m(s, g): 세션 s 의 훅이 돌 때마다(SessionStart·UserPromptSubmit·Stop) 그때의 g(s) 로 만든다. 같은 사실은 한 번만 있다.
  - 지움 사실 z(s, g): `source = clear` 인 SessionStart 가 s 에서 돌 때 만든다.
- clear 로 난 파일: T(s) 의 첫 대화 줄(메타 줄과 isMeta 를 뺀 첫 사용자 줄)이 `<command-name>/clear</command-name>` 이면 s 는 clear 로 났다. T(s) 하나만 보고 정한다.
- 부모: s 가 clear 로 났으면 p(s) = argmax_{s′} max{θ(ℓ) : ℓ ∈ T(s′), θ(ℓ) < θ₀(s)} 이다. 범위는 m(s′, g) 이 있고 s′ ≠ s 인 s′ 이고, g 는 z(s, g) 의 g, θ₀(s) = T(s) 첫 줄의 θ 다. 곧 「s 가 나기 직전에 그 무리에서 줄이 쓰인 transcript」다.
  - 이것은 기록된 시각 위의 최댓값(집합 함수)이다. 처리·도착 순서가 아니다. M11 이 막는 「가장 최근」은 도착 순서다(이 해석은 L1 에서 적는 것이고 시험 결과를 본 뒤가 아니다).
  - 재개 뒤 다시 지우는 경우(T1 → clear → T2 → T1 재개 → clear → T3): T3 이 나기 직전에 줄이 쓰인 것은 T1 이므로 p(T3) = T1 이다. θ₀ 최댓값(T2)을 고르면 틀린다. 그래서 「마지막 줄의 시각」으로 정의한다.
  - clear 로 났는데 z(s, ·) 가 없으면 p(s) 는 정의되지 않는다 → C(T(s)) 를 짓지 않는다 → 복원은 오류다(M11).
  - clear 로 나지 않았으면 부모가 없다(새 대화·서브에이전트 파일·재개는 같은 파일).
- C(T(s)) 의 `session_meta` = `{id: s, forked_from_id: p(s), forked_from_ordinal_exclusive: c(s)}` 다. c(s) = C(T(p)) 에서 「θ ≥ θ₀(s) 인 첫 원본 줄」의 첫 롤아웃 순번이다(없으면 끝 + 1). 부모가 나중에 재개되어 붙는 줄은 s 의 계보에 들어가지 않는다.
- 계보 Λ(s) 는 libvrs 의 포크 정의 그대로다(조상 구간을 자식의 c 로 자름). libvrs 에 새 개념을 넣지 않는다.
- 전제(관측이 아직 없음 → L4 확인):
  - P-H 데스크톱 세션의 pid 파일은 `/clear` 뒤에도 같은 `hostSessionId` 를 갖고 `sessionId` 만 새 것으로 바뀐다.
  - P-C 대화형 화면의 `/clear` 도 새 파일의 첫 대화 줄로 `/clear` 명령 줄을 남긴다.
  - P-1 한 무리에서 한 시각에 줄이 쓰이는 transcript 는 하나다.

**C5 턴.** libvrs D8 그대로다(시작 = `task_started`, 끝 = 다음 `task_started` 또는 `task_complete`). C2 가 시작·끝을 이렇게 놓는다.
- 시작: 발화가 든 사용자 줄, 「Stop hook feedback」 isMeta 줄.
- 끝: `end_turn` 인 text 블록 줄, API 오류 줄, 끊김 줄.
- 그래서 `/clear` 직전 실행이 정상 종료·오류·끊김 가운데 무엇으로 끝났든 그 턴은 부모 파일 안에서 닫힌다(L1 끝 (b)). 셋 다 아닌 채 `/clear` 된 턴(도구 실행 중 지움 등)은 열린 채 남아 기억이 되지 않는다. 결함 KT1(무관, L4 에서 셈)로 둔다.
- `end_turn` 메시지에 text 블록이 둘 이상이면 첫 text 뒤에서 턴이 닫히고 뒤 text 는 턴 밖이 된다. 결함 KT2(무관, L4 에서 셈)로 둔다.

**C6 도구.** 서버 하나에 두 개다. 둘 다 요청별 상태가 없다.
- `vrs_restore(session?, budget?, start?)`
  - s = `session` 이 있으면 그것, 없으면 부른 쪽. 부른 쪽 = 이 서버를 띄운 Claude 프로세스의 pid 파일에 지금 적힌 `sessionId`. 찾지 못하면 오류다. 추측(가장 최근 파일 등)하지 않는다.
  - 값: A = `vrs_assemble_b(C(T(s)), budget)`(budget 없으면 libvrs 기본 258,400). 결과 항목 = A 의 payload 가운데 원본 줄이 **s 의 살아 있는 문맥 밖**인 것이다. 살아 있는 문맥 = T(s) 에서 마지막 `compact_boundary` 뒤의 줄(없으면 T(s) 전부). 곧 조상 파일의 항목과 압축 경계 앞 항목이다. 표지 줄(task_started·task_complete)은 원문이 없으므로 내지 않는다.
  - 항목마다 원본 위치 `T#o+n`, 블록 k, θ, 종류, 본문(payload 의 글을 JSON 에서 푼 것)을 낸다. 순서는 계보 위치(조상 → 자손, 파일 안 o)다.
  - 첫 줄은 표지 「⟦vrs-restore v1 · 계보 … · 항목 K · 토큰 T · start=… · next=…⟧」다. 이 표지가 C2 의 복원 표지다.
  - 쪽: 응답이 호스트의 도구 출력 상한 R 을 넘으면 계보 위치 순으로 앞에서부터 R 까지 내고 `next` = 다음 항목의 위치 키를 적는다. `start` 를 주면 그 위치 키부터 낸다.
  - 오류: s 를 모름, C(T(s)) 를 지을 수 없음(C4 부모 미정), libvrs rc 1 을 `vrs_wait` 상한 안에 못 벗어남, rc 2·음수, 결과 항목의 sha 가 원본과 다름. 오류 때는 부분 결과를 내지 않는다.
- `vrs_read(path, start, end)`
  - 루트(transcript 루트, 메모리 문서 루트) 아래 파일의 바이트 [start, end) 를 그대로 낸다. sha256 을 붙인다. 상한 R 을 넘으면 앞에서부터 줄 경계까지 내고 `next` 를 적는다.
- 옛 질의 회수 도구는 옛 서버(swegca-vrs2)에 그대로 있다. 새 서버는 그 이름을 쓰지 않는다.
- 새 문맥 안내: SessionStart(`clear`) 훅이 `additionalContext`(10,000자 안)로 「이 문맥은 /clear 로 새로 열렸다. 이어 가려면 vrs_restore 를 먼저 부른다」 한 문단을 넣는다. 복원 내용 자체는 훅으로 넣지 않는다(상한 10,000자).

### 7.3 증명 (손으로)

**T-m1 (M2 원본 정확).** vrs_restore 의 항목 본문은 그 위치 원본 줄의 필드 값과 바이트로 같다.
- conv 는 ℓ 의 JSON 필드를 골라 payload 에 옮길 뿐이다(text·input·content·prompt·rendered.content). 값을 짓는 경우는 표지 줄(task_started·task_complete)과 rendered 의 이음(개행)과 복원 표지 하나뿐이다. 표지 줄은 출력에서 뺀다.
- libvrs 는 고른 줄의 payload 를 파일에서 읽어 그대로 돌려준다(lib7 성질, M1 이 Windows 에서도 같음을 보인다).
- 출력은 payload 의 id `cc1:o:k` 로 원본 위치를 얻고, payload 글을 JSON 에서 풀어 낸다. 푸는 일은 conv 가 옮길 때 한 JSON 인코딩의 역이다.
- 원본이 바뀌었으면(P-A 깨짐) `cc.h` 와 지금 바이트의 sha 가 다르므로 오류다. 그래서 낸 본문은 지금 원본의 필드 값이다. ∎
- 남는 것: rendered 는 여러 content 를 개행으로 이은 것이라 「한 필드 값」이 아니라 「필드 값들의 이음」이다. 출력에 그 사실을 종류로 적는다.

**T-m2 (M3 발화 온존).** 사람이 친 글은 모두 K_USER 항목이 된다. 단 하나의 예외가 있다.
- 사람이 친 글이 transcript 에 남는 길은 둘이다. 사용자 줄의 발화 블록(isMeta 아님·도구 결과 아님·로컬 명령 아님·끊김 아님), 그리고 `queued_command` 의 prompt 다. C2 는 둘 다 user 메시지로 보낸다.
- libvrs 는 user 메시지를 kind_of 로 다시 가른다. 글의 첫 글자가 `<`(image 제외)이고 글 전체가 완전한 `<태그>…</태그>` 블록들뿐이면 K_DEV 로 본다. 그런 발화만 빠진다. 결함 KU1(무관, L4 에서 수를 센다. 0이 아니면 L1 로 돌아온다)로 둔다.
- K_USER 항목이 조립에 다 들어가는 것은 libvrs C3′ 의 조건(발화 합 ≤ B_P) 아래서다. 이 조건은 lib 의 것이고 여기서 바꾸지 않는다. M3 의 판정은 그 조건 안에서 한다. ∎

**T-m3 (M4 실시간).** 부른 시점 t 에 T 에 개행까지 쓰인 줄은 C1 의 S_t 에 든다. 그러면 conv 는 그 줄만 보고 정해지고, C3 의 위치는 그 줄 앞의 줄 집합으로 정해진다. 그래서 A(S_t) 의 입력에 들어간다. 「들어가게 하는 절차」(꼬리 읽기)는 L2 의 몫이다. 정의는 도구 값이 S_t 의 함수라는 것이다. ∎
- 공식 문서는 「transcript 는 비동기로 쓰여 메모리의 대화보다 늦을 수 있다」고 한다. 그래서 M4 는 「파일에 쓰인 줄」 기준이다. 아직 파일에 안 쓰인 현재 턴의 일부는 S_t 에 없다. 그것은 부른 쪽의 살아 있는 문맥에 있으므로 복원 대상도 아니다.

**T-m4 (M5 모양).** 두 도구의 입력에는 스냅숏 id·handle·cursor·release 가 없다. 값은 (인자, S_t, 사실 집합)의 함수다. 그래서 그 사이 새 줄과 새 사실이 없으면 같은 응답이다. 질문 하나(「이어 갈 것을 달라」, 「이 위치를 보여 달라」)는 쪽이 하나면 호출 하나로 끝난다. ∎

**T-m5 (M11 이음).** z(s, g) 가 있으면 p(s) 는 하나로 정해진다. P-1 아래에서 그것은 `/clear` 를 누른 그 transcript 다.
- z 는 그 clear 를 한 프로세스의 무리 g 를 든다. 그 무리의 transcript 가운데 θ₀(s) 직전에 줄이 쓰인 것이 argmax 다. P-1 로 그 시각에 줄을 쓰던 transcript 는 하나다. `/clear` 직전까지 대화하던 transcript 다.
- 다른 무리(다른 데스크톱 세션·다른 CLI 프로세스)의 transcript 는 m(·, g) 가 없어 후보가 아니다. 그래서 다른 세션으로 잇는 일은 생기지 않는다.
- z 가 없으면 정의되지 않고 오류다. 추측으로 잇지 않는다. ∎

**T-m6 (M12 자기 참조 없음).** 복원 도구의 결과는 새 transcript 에 tool_result 로 다시 적힌다. C2 는 복원 표지로 시작하는 tool_result 를 표지 한 줄로 보낸다. 그래서 그 결과에 담긴 조상 항목의 본문은 C(T(s)) 에 다시 들어가지 않는다. 같은 원본이 두 경로로 세지는 일이 없다. call_id 짝(function_call ↔ output)은 그대로 남는다. ∎

**T-m7 (M13 크기).** S_t 와 사실 집합이 그 사이 바뀌지 않으면 결과 항목 목록 L 은 하나다(T-m4). 쪽 k 는 L 의 [start_k, next_k) 구간이고, next_k = start_{k+1} 이다. 그래서 쪽들을 이으면 L 이고, 한 번에 받은 것과 바이트로 같다. ∎
- 다른 세션에서 턴이 닫히면 libvrs 의 패턴 셈이 바뀌어 다음 쪽의 L 이 달라질 수 있다. 이것은 정의의 성질이다. 그래서 M13 의 판정은 「사이에 바뀌지 않은」 경우에 하고, 바뀐 경우는 각 응답이 각자 시점의 정확한 값이다(표지에 계보·항목 수를 적어 바뀜이 보인다). 이 해석도 L1 에서 적는 것이다.
- 호스트 상한 R 을 조립 크기 이상으로 올릴 수 있으면 쪽이 하나다(클로드 코드는 L2 에서 설정을 확인한다).

**T-m8 (M7 비용, 정의 쪽).** 각 값의 근거가 유한하다.
- conv(ℓ) 는 ℓ 하나다.
- 순번·위치는 o 로 매긴 합이다. 합이 바뀌는 것은 새 줄이 붙을 때 그 뒤 위치뿐이고, P-A(덧붙이기 전용)로 새 줄은 늘 끝에 붙는다.
- p(s) 는 무리 하나의 transcript 수 × (각 파일에서 θ₀ 아래 최댓값 찾기)다. 무리의 transcript 수는 그 데스크톱 세션의 `/clear` 횟수 + 1 이다. 전체 저장소 크기 N 과 무관하다.
- vrs_restore 는 libvrs 조립 하나와 출력 크기만큼의 풀기다. 조립 비용은 libvrs 의 T-int-8 쪽이다.
- 절차의 비용식(꼬리 읽기·합을 어떻게 셈)은 L2 에서 보인다. ∎

**T-m9 (직렬 구조 없음).** conv 는 국소다. 순번·위치는 o 순위 위의 합, 턴 표지는 국소, 부모는 기록된 θ 위의 최댓값, 사실은 만들기 전용 집합이다. 도구 값은 집합의 함수다. 어떤 정의에도 처리·도착 순서·세대 카운터·사슬·단일 쓰기 주체가 없다. ∎

### 7.4 L1-A 끝 조건 점검
- (a) ✓ C2(관측된 줄 종류 전부와 처음 보는 종류는 뺌 + 셈), 되돌림 = payload id → (T, o, k).
- (b) ✓ C4·C5(재개 = 같은 파일, clear = 포크, 서브에이전트 = 제 계보, 압축 경계 = 살아 있는 문맥의 경계).
- (c) ✓ C6.
- (d) ✓ T-m1–T-m8.
- (e) ✓ T-m9.
- (f) ✓ 이음 열쇠는 관측(pid 파일·clear_session 설명·격리 실행)에 근거하고, 관측이 아직 없는 P-H·P-C·P-1 은 전제로 적혀 L4 항목이 된다.
- **L1-A 끝.** L1 전체의 끝은 L1-B(§8)까지다.

### 10.2 정의 (lib7 정의는 그대로 두고 더하기만 한다)

기호는 시냅스 문서 그대로다. x 는 요청의 열린 턴(또는 패턴 셈에서는 닫힌 턴), t = θ₀(x), 𝔅_t = {y ∈ 𝔅 : θₑ(y) ≤ t}, K = cue_set, V(y) = 턴 보기(요청 1500 + 최종답 2500), Λ(x) = x 의 계보.

**G1 보기 내용 정체.** v(y) = V(y) 의 바이트 해시다. 같은 v 를 가진 턴들을 한 「보기」로 본다. 𝔙_t = {v(y) : y ∈ 𝔅_t}.
- 이유: 포크 복사·같은 프롬프트 재사용 같은 복사본이 희귀 판정과 출력을 부풀리지 않게 한다(끝 조건 (f)).

**G2 전역 질문 단서.** Q_g(x) = Q(x) ∩ K(V(x)) — 닫힌 x 의 패턴 셈에서 쓴다. 열린 x₀ 의 고르기에서는 V(x₀) 가 아직 없으므로 Q_g(x₀) = Q(x₀) 다.
- 교집합을 두는 이유는 (d) 의 상한 증명이 「h ∈ Q_g(x) 이면 x 자신이 h 의 빈도에 든다」를 쓰기 때문이다(T-g3). lib7 의 Q(x) 는 바꾸지 않는다.

**G3 전역 빈도와 드문 단서.**
- df^𝔅_t(h) = |{v ∈ 𝔙_t : h ∈ K(보기 v)}|. 보기 내용 단위로 센다.
- R_g(x) = {h ∈ Q_g(x) : 1 ≤ df^𝔅_t(h) ≤ F}, F = 8 (lib7 의 F 그대로).
- Y_g(h) = {y ∈ 𝔅_t \ Λ(x) : h ∈ K(V(y))}. 계보 밖 턴만 든다. 계보 안 턴은 lib7 몫이 이미 다룬다.

**G4 전역 내용 열쇠와 칸.**
- sh_g(x, y) = |{h ∈ R_g(x) : h ∈ K(V(y))}| (y ∈ 𝔅_t \ Λ(x)).
- 열쇠 κ_g = (g, min(sh_g, 16)). sh_g ≥ 1 일 때만 있다. 칸 16개를 새로 둔다. lib7 의 칸(NCA 4,266)과 겹치지 않는 새 번호다.
- 쌍 (x, y) 는 x 가 닫혔고 y ∈ 𝔅_{θ₀(x)} \ Λ(x) 이고 κ_g 가 있을 때 κ_g 칸에 든다. 판정 J(x, y)·관찰자·규칙′·강도는 lib7 그대로다(J 는 두 턴만 읽고 계보를 보지 않는다).
- 출처 다양성 s 는 lib7 그대로(x 의 계보 뿌리 수, 2 에서 멈춤)다.
- **lib7 칸은 이 쌍을 받지 않는다.** 그래서 lib7 의 모든 칸 값은 lib7 과 같다.

**G5 전역 먼 집합.** 요청 x₀ 에서 lib7 의 N₃·T₃·N_far 를 먼저 그대로 정한다.
- 덮임: h ∈ R_g(x₀) 는 Y_g(h) 가운데 보기 v 가 T₃ ∪ N_far 의 어떤 턴의 보기와 같은 것이 있으면 덮였다.
- 승인 원소 Ap_g(x₀) = {(y, 답) : y ∈ 𝔅_t \ Λ(x₀), (y, 답) 이 κ_g 칸으로 규칙′ 승인됨}.
- 세기 σ_g(x₀, y) = Σ_{h ∈ R_g(x₀) ∩ K(V(y))} ln(|𝔙_t| / df^𝔅_t(h)). |𝔙_t| ≥ df 이므로 항은 0 이상이다.
- M_g(h) = 덮이지 않은 h 마다 Y_g(h) 안에서 (y, 답) ∈ Ap_g 인 y 가운데 σ_g 최댓값을 갖는 **보기**들의 집합. 같은 보기의 턴이 여럿이면 그 가운데 κ 순서(θₑ, 경로, ord0)가 가장 작은 턴 하나를 대표로 둔다. 동점인 서로 다른 보기는 모두 넣는다(lib7 의 「동점 전부」).
- N^g_far = {(대표 y, 답) : 보기 ∈ ∪_h M_g(h)}.
- 예산: lib7 의 조립을 먼저 짓는다. 남은 예산 B − 사용량 안에서 N^g_far 를 σ_g 내림차순(같으면 κ 순서)으로 넣는다. 이 우선 순서는 원소들의 전순서이고 처리 순서가 아니다.
- 출력 = lib7 출력 ∪ (넣은 N^g_far). 전역 몫 원소는 출력에서 「전역」 표지를 단다(MCP 가 계보 몫과 구별해 보여 줄 수 있게).

### 10.3 증명 (손으로)

**T-g1 (lib7 몫 그대로, 끝 조건 (b)).**
- lib7 의 칸 값은 lib7 의 쌍(계보 후보)으로만 정해진다. G4 의 쌍은 새 칸에만 든다. 그래서 칸 값이 같다.

- 출력에서 「전역」 표지 원소를 빼면 lib7 출력이다. ∎

**T-g2 (요청 하나의 크기, 끝 조건 (c)).**
- |Y_g(h)| 의 서로 다른 보기 수 ≤ df^𝔅_t(h) ≤ F 다.
- 그래서 |M_g(h)| ≤ F 다(보기마다 대표 하나).
- |N^g_far| ≤ F · |R_g(x₀)| ≤ F · |Q(x₀)| 다. lib7 P3″ 의 |Q| 상한(3000)을 따른다. N·계보 길이와 무관하다. ∎

**T-g3 (늦은 턴의 영향, 끝 조건 (d)).** 턴 z 가 𝔅 에 들어온다. 영향은 z 의 보기 단서 h ∈ K(V(z)) 의 df 가 하나 늘 수 있는 것뿐이다. 보기 v(z) 가 이미 있으면 df 는 안 바뀌고 Y_g 에 같은 보기의 턴 하나가 더해진다. 대표는 κ 최소라 바뀔 수 있다.
1. 다시 세야 하는 것은 「h ∈ Q_g(x) 이고 t_x = θ₀(x) ≥ θₑ(z) 이며, z 때문에 h 의 드묾(1 ≤ df ≤ F)이 바뀌거나 Y_g(h) 가 바뀌는」 닫힌 x 의 쌍이다.
2. 그런 x 의 수를 센다. G2 로 h ∈ Q_g(x) 이면 h ∈ K(V(x)) 다. 그래서 x 자신의 보기도 θₑ(x) 뒤 시각의 df 에 든다.
3. 그런 x 들을 θ₀ 순으로 놓자. 보기가 서로 다른 x 가 F + 1 개 닫힌 뒤에 시작한 x 에서는 df^𝔅 ≥ F + 1 이다. 그래서 h 는 z 가 있든 없든 드물지 않고, 쌍이 바뀌지 않는다.
4. 바뀔 수 있는 x 는 「앞서 닫힌 h-보기가 F 개 이하인 시점에 시작한」 x 다. 그런 x 는 다음 두 부류뿐이다.
   - 그 자신이 그 F + 1 개 안에 드는 x: F + 1 개 이하다.
   - 그 F + 1 개가 다 닫히기 전에 시작해 아직 열려 있던 x: 같은 시각에 열려 있는 턴 수 C(동시에 대화하는 세션 수)로 묶인다.
   - 같은 보기의 복사본 x 들은 df 를 하나만 올린다. 그러나 G1 의 보기 단위라 셈은 보기 단위로 같다. 복사본 x 들은 같은 Q_g 와 같은 V 를 가져서 쌍 값이 같고, 다시 세기도 한 번 계산을 나눠 쓸 수 있다(L2).
5. 그래서 단서 하나당 다시 볼 x 의 보기 수 ≤ F + 1 + C 다. z 하나에 대해 ≤ |K(V(z))| · (F + 1 + C) 다. |K(V(z))| 는 보기 크기(4000자)로 묶인다.
6. 관찰자 쪽(D9 창이 바뀌는 y, T-int-8: ≤ W − 1 + T)에서 y 를 상대로 한 전역 쌍도 다시 센다. y 하나의 전역 쌍 수 = y 와 드문 단서를 나눈 x 의 수 ≤ |K(V(y))| · (F + 1 + C) 다(4 와 같은 논증).
7. 합: 늦은 턴 하나의 전역 몫 일 ≤ |K(V(z))|·(F+1+C) + (W−1+T)·|K(V)|·(F+1+C). N·계보 길이가 없다. ∎
- D4′ 의 4096 지평은 전역 쌍에 필요 없다. 상한이 단서의 드묾에서 나오기 때문이다.
- C 는 「동시에 열려 있는 턴 수」다. 사용자 수·세션 수로 묶이고 이력과 무관하다. lib7 의 T(같은 θₑ 무리 크기)와 같은 부류다.

**T-g4 (P1v2 그대로, 끝 조건 (e)).** P1v2 의 증명은 (i) r ∈ E^W_y 라 r 이 y 를 쓸 수 없음, (ii) 가정 A1(무관한 쌍에서 S_x·S_r 의 자리를 바꿔도 결합 분포가 같음)만 쓴다(일체화 T-int-9, 시냅스 L224–238).
- (i): 관찰자는 lib7 그대로라 같다.
- (ii): A1 은 쌍이 어떤 열쇠로 칸에 들어왔는지 쓰지 않는다. 그래서 전역 칸에서도 같은 꼴로 선다.
- 그래서 P(전역 칸 승인 | 무관, A1) < 0.0363 이다. ∎
- 위험(증명이 아니라 가정의 그럴듯함): 계보 밖 쌍에는 같은 틀 글(훅 문구·복사된 지시)을 나눈 턴이 많다. 이것이 A1 을 약하게 만들 수 있다. 보기 V(y) 는 요청 + 최종답이고 주입을 담지 않는다. 그래서 훅 문구는 V 에 잘 안 들어간다. 그래도 L4 에서 「전역 승인 칸의 근거 단서」를 표본으로 보고한다(통과 조건이 아니라 관측).

**T-g5 (복사본, 끝 조건 (f)).** df^𝔅 는 보기 내용 단위로 센다. 그래서 같은 보기의 턴 k 개는 df 를 1 만 올린다. M_g 는 보기마다 대표 하나만 낸다. 그래서 출력에 같은 보기의 답이 두 번 들지 않는다. ∎
- lib7 몫(계보 안)과 전역 몫 사이: 전역 후보는 계보 밖뿐이다. 그러나 계보 안 턴과 보기가 같은 계보 밖 턴(포크 복사)이 있을 수 있다. 그런 h 는 G5 의 덮임 규칙(같은 보기가 T₃ ∪ N_far 에 있으면 덮임)으로 빠진다. 그 보기가 계보 안에서 아직 출력에 없으면 전역으로 들어올 수 있다. 그것은 같은 내용이 한 번 들어가는 것이다(계보 안 그 턴은 출력에 없으므로 두 번이 아니다). ∎

**T-g6 (직렬 없음, 끝 조건 (g)).** 𝔙_t·df·R_g·Y_g·sh_g 는 집합의 크기·교집합이다. 대표는 κ 전순서의 최소, M_g 는 최댓값, 예산 채움은 원소 전순서다. 칸 값은 쌍 집합 위의 합(lib7 D11 그대로)이다. 처리·도착 순서가 없다. ∎

- MCP 서버의 부모 사슬(이번 세션, PowerShell Win32_Process): `swegca-vrs2-mcp.exe`(10472) ← `claude.exe`(5820), 그 아래 python 2단. claude.exe 의 pid 로 `~/.claude/sessions/5820.json` 이 있다. 곧 서버에서 위로 1–3단 올라가면 pid 파일이 있는 프로세스가 나온다.
- lib7 의 세션 정체 씨앗은 `ident_hash` = `fid_key(경로)`(파일 이름의 id) 또는 `fnv(rel)`(sessions 폴더 기준 상대 경로)이다(vrs_lib.cpp.src 3807–3810). 𝔅 의 같은 θₑ 순서는 `fs::path` 비교다(1320). 그래서 Windows 와 리눅스가 같은 상대 경로 문자열(구분자 `/`)을 쓰면 씨앗과 순서가 같다.
- lib7 의 파일 시스템 사용: `fs::` 9곳(재귀 디렉터리 순회 3, create_directories 3, path 비교 1, …). 경로는 `std::string` 이다. MinGW 의 `fs::path(std::string)` 은 그 문자열을 ANSI 코드 페이지(이 PC 는 CP949)로 읽는다. 경로에 한글(「새 폴더」)이 있어서 그대로는 깨진다.
- lib7 의 리눅스 자리(G 단계 §0): mmap 1, futex 대기·깨우기 2, realpath 4, inotify 감시 1, eventfd 정지 1, pread/open/O_APPEND write 몇 곳, CPU 고정.
- 16바이트 atomic: 이 도구 사슬의 `std::atomic<16B>` 는 잠금이다(§5). lib7 은 쓰지 않는다.
- 호스트 도구 출력 상한: 클로드 코드는 `MAX_MCP_OUTPUT_TOKENS`(기본 25,000 토큰, 10,000 넘으면 경고)를 둔다. **내 지식이고 이번에 문서로 확인하지 않았다.** L3 첫 일로 공식 문서를 확인한다(KM1).

### 13.2 (A) Windows 플랫폼 층
- 헤더 하나(`vrs_plat.h`)에 함수 열한 개를 두고, lib7 소스의 리눅스 자리만 그 함수 호출로 바꾼다. 리눅스 빌드에서 그 함수는 원래 호출 그대로다. 그래서 리눅스 빌드의 동작은 바뀌지 않는다(L3 에서 리눅스 재빌드로 lib7 시험을 다시 통과시켜 보인다).

| 자리 | 리눅스 | Windows |
|---|---|---|
| 조각 읽기 보기 | `mmap(PROT_READ, MAP_PRIVATE)` / `munmap` | `CreateFileMappingW` + `MapViewOfFile(FILE_MAP_READ)` / `UnmapViewOfFile` |
| 진행 대기·깨우기 | futex WAIT/WAKE on `progress` | `WaitOnAddress` / `WakeByAddressAll` (Windows 8+, 같은 뜻: 값이 같을 때만 잠듦, 시간 상한) |
| 실제 경로 | `realpath` | `CreateFileW`(FILE_FLAG_BACKUP_SEMANTICS) + `GetFinalPathNameByHandleW` → `\\?\` 머리 떼기 → UTF-8 |
| 디렉터리 감시 | inotify(MODIFY·CLOSE_WRITE·CREATE·MOVED_TO) + poll | `ReadDirectoryChangesW`(하위 포함, FILE_NAME·LAST_WRITE·SIZE) + OVERLAPPED 사건 |
| 정지 신호 | eventfd | 수동 재설정 사건 + `WaitForMultipleObjects`(감시 사건, 정지 사건) |
| 위치 읽기 | `pread` | `ReadFile` + OVERLAPPED 위치(공유 READ·WRITE·DELETE) |
| 덧붙이기 | `open(O_APPEND)` + `write` | `CreateFileW(FILE_APPEND_DATA)` + `WriteFile` 한 번(로컬 NTFS 에서 한 호출의 덧붙이기는 섞이지 않음) |
| 읽기 열기·크기 | `open(O_RDONLY)`, `fstat` | `CreateFileW(GENERIC_READ, 공유 셋 다)`, `GetFileSizeEx` |
| CPU 고정 | `pthread_setaffinity_np` | `SetThreadAffinityMask` |
| 경로 글자 | `std::string` 그대로 | 모든 `fs::path` 를 UTF-8 → UTF-16 으로 만든다. `fs::path` 에서 나오는 글은 UTF-8 로 받는다 |
| 상대 경로 구분자 | `/` | `rel` 을 만들 때 `\` → `/` 로 맞춘다(씨앗·조각 이름이 리눅스와 같아짐) |

- 정의 코드(조립·시냅스·색인·D1–D11)는 한 줄도 바뀌지 않는다. 바뀌는 줄은 위 표의 호출 자리와 include 뿐이다(E2-4).
- 공유 모드: 원본 transcript 는 클로드 코드가 쓰는 중에 읽는다. 그래서 모든 열기는 FILE_SHARE_READ·WRITE·DELETE 를 준다.
- 잠금 점검(L3 끝 조건, §5): 산출물에 `libat_lock_n`·`__atomic_*_16`·`pthread_mutex_lock` 참조가 0개다.

**lib 에 더하는 것 하나(정의가 아님).** `vrs_wait_off(h, path, off, timeout_ms)`: 「그 파일의 처리된 앞부분(pub)이 off 를 덮었다」를 기다린다. 기존 `vrs_wait` 와 같은 진행 단어로 잠든다.
- 왜 필요한가: M4. `vrs_insert` 는 줄을 넘기기만 하고, 그 줄이 처리된 앞부분에 들기 전에 돌아올 수 있다(일체화 §7.6 「vrs_insert 가 돌아올 때 pend == 0 은 없다」).
- 정의가 아닌 이유: 이미 있는 상태(pub)를 읽기만 한다. 조립·셈·판정 어디에도 쓰지 않는다. 기다림의 상한은 그 꼬리 처리 비용이다(V5-05 (a) 와 같은 꼴).

### 13.3 (B) 변환기
- 위치: 데몬 안의 C++ 코드다. 파이썬으로 짓지 않는다. 한 프로세스 안의 파이썬 스레드는 GIL 로 직렬이 된다(「병렬처럼 보이는 직렬」).
- 파일 하나의 상태는 **변환된 파일 C(T) 자신**이다. 따로 둔 커서는 없다.
  - C(T) 의 마지막 완전한 줄(개행으로 끝남)의 `cc.o + cc.n` = 덮은 원본 끝 e_T, 그 줄의 순번 = k_T, C(T) 의 그 줄 끝 바이트 = s_T.
  - 셋 다 C(T) 끝에서 거꾸로 한 줄만 읽어 얻는다. O(1) 이다.
- **꼬리 변환 conv_tail(T):**
  1. e_T·k_T·s_T 를 읽는다.
  2. T 의 [e_T, EOF) 를 읽어 완전한 줄만 가른다.
  3. 줄마다 C2′ 의 conv(ℓ) 를 짓는다. 순번은 k_T + 1 부터 매기고, 순번은 10자리 고정 폭이다.
  4. 지은 바이트 전체를 위치 s_T 에 쓰기 한 번(`WriteFile` + OVERLAPPED 위치)으로 쓴다.
  5. 줄마다 `vrs_insert(C(T), 위치, 줄)` 한 뒤 `vrs_written` 한다.
- **여럿이 같은 T 를 동시에 변환해도 같다.**
  - conv 와 순번·위치는 원본 바이트와 시작점의 순수 함수다.
  - 두 실행이 같은 시작점에서 출발하면 같은 위치에 같은 바이트를 쓴다. 앞 시작점에서 출발한 쪽은 이미 쓰인 바이트를 같은 바이트로 다시 쓴다. 그래서 어떤 겹침에서도 파일 내용이 같다. 잠금·주인이 필요 없다.
  - `vrs_insert` 는 (경로, 위치)마다 멱등이다(lib7).
  - 쓰기는 늘 기존 끝(≤ EOF)의 완전한 줄 경계에서 시작한다. 그래서 중간 구멍이 생기지 않는다.
  - 늘어나는 동안 잠시 보이는 0 바이트는 lib7 의 「NUL 에서 멈춤」(nul_stops)이 다룬다.
  - 죽어서 남은 반쪽 줄은 다음 실행이 마지막 완전한 줄 끝에서 다시 쓴다.
- **큰 꼬리(첫 짓기·오래 꺼져 있던 뒤)의 병렬 변환.** 꼬리가 문턱(예: 8 MB)보다 크면 다음 순서로 한다.
  - 줄 경계에서 덩어리 m 개로 나눈다.
  - 덩어리마다 conv 를 따로 지어 (줄 수, 바이트 수)를 얻는다. 서로 독립이라 병렬이다.
  - 덩어리 m 개의 (줄 수, 바이트 수)를 앞에서부터 더한 합을 낸다. O(m) 이고 m = 꼬리 크기 / 덩어리 크기다.
  - 덩어리마다 제 위치에 쓴다. 이것도 병렬이다.
  - 정의 C3 의 「o 로 매긴 합」을 병렬 앞부분 합으로 계산하는 것이다.
- **바뀐 파일 집합(일 집합).** 감시 사건이 오면 그 파일의 번호 i 에 대해 2단 비트맵의 비트를 원자 OR 로 켠다.
  - 아래 단은 파일마다 비트 1, 위 단은 아래 단의 64비트 낱말마다 비트 1 이다.
  - 상주 일꾼 W 개(`WaitOnAddress` 로 잠듦)가 위 단에서 켜진 낱말을 원자 교환(0 으로)으로 가져가 그 파일들의 conv_tail 을 한다.
  - 가져가는 순서는 정의에 없다. 비트를 끈 뒤 변환하므로 그 사이 온 사건은 비트를 다시 켜 다음에 잡힌다(빠지는 사건 없음).
  - FIFO 가 아니고 주인이 없다.
  - 파일 번호는 경로 → 번호 해시표(CAS 로 끼움)로 얻는다.
- **비용.** 줄이 붙는 사건 하나의 일은 이렇다.
  - 비트 OR 2번 + 낱말 교환
  - 꼬리 바이트 파싱·쓰기
  - 줄마다 `vrs_insert`(lib7: O(log L_f))
  - 파일 수·이력에 비례하는 항이 없다.
  - 위 단은 켜진 낱말만 훑는다. 크기는 파일 수 / 4096 낱말이다(이 PC 1,793 파일 → 1 낱말). 더 커지면 위 단을 다시 쪼개 log₆₄ 로 둔다.

### 13.4 (C) 상주 데몬
- 하나의 프로세스가 lib7 핸들 하나, 변환기, 감시(`~/.claude/projects` 전체 하위), 요청 통로를 가진다.
  - 여러 클로드 세션이 각자 lib 핸들을 열면 색인 표가 세션 수만큼 RAM 에 실린다. 같은 롤아웃을 세션 수만큼 변환하는 일도 생긴다(E2-2). 그래서 하나로 둔다.
  - 프로세스는 하나라도 쓰기는 여러 스레드가 한다. 단일 쓰기 주체가 아니다(변환은 멱등, lib 은 잠금 없음).
- **요청 통로:** 이름 붙은 파이프 `\\.\pipe\vrs-lib-<사용자>`. 연결마다 그 연결의 스레드가 요청 하나를 받아 답한다. 연결 사이에 공유하는 요청 상태가 없다. 큐 없음.
- **시작:** 다리가 통로에 연결하지 못하면 데몬을 분리 실행한다.
  - 둘이 동시에 띄우면 `FILE_FLAG_FIRST_PIPE_INSTANCE` 로 첫 파이프를 만든 쪽만 남고, 다른 쪽은 바로 끝난다. 운영체제가 주는 이름 하나의 유일성이지, 우리가 거는 잠금이 아니다.
  - 데몬이 뜨는 동안 다리는 연결을 몇 번 다시 시도한다(상한 M8 의 5 s).
- **재기동(M8):**
  1. `vrs_open`(lib7 P-2: 조각 mmap + 꼬리, 상주 일꾼)과 변환기 꼬리 잡기를 함께 시작한다.
  2. 변환기 쪽: 모든 T 의 비트를 켠다. 일꾼이 각 conv_tail 을 한다. 파일마다 C(T) 끝 한 줄 읽기 + 꺼져 있던 동안 붙은 꼬리다.
  3. 요청은 `vrs_wait(C(T))` 가 0 일 때 시작한다(rc 1 을 상한 안에서 기다림, V5-05 (a)).
  - 어림: 파일 수 × (끝 한 줄 읽기) + 꼬리 합 + lib7 복원(일체화 E2-1, 조각 ≤ 100 MB 에 1 s 안팎). 끝 한 줄 읽기 1,793번은 어림 1 s 안이다. 그래서 5 s 안이다.
  - 파일 수 항이 남는다. 재기동은 사건이 아니라 한 번의 일이라 「이벤트당 비용」 결함은 아니다. 다만 파일 수에 따라 자라는 것은 적어 둔다(KR1, 무관, L4 에서 잰다).
- **첫 짓기(설치 때 한 번):** 2.4 GB 를 13.3 의 병렬 변환으로 하고, lib7 이 롤아웃에서 색인을 짓는다. 그동안 요청은 rc 1 을 상한 안에서 기다리고, 넘으면 오류다. 재기동이 아니라서 M8 대상이 아니다.

### 13.5 (D) MCP 다리와 도구
- 다리 = 클로드 코드가 세션마다 띄우는 stdio MCP 서버다. 얇은 파이썬이다(세션마다 따로 프로세스라 GIL 이 세션 사이를 직렬로 만들지 않는다). tools/list 에 vrs_restore·vrs_read 를 낸다. tools/call 은 데몬에 한 번 묻고 답을 그대로 돌려준다.
- **부른 쪽 정체(C6):**
  1. 다리 프로세스에서 부모를 1–4단 올라간다(Toolhelp32 스냅숏).
  2. pid 파일 `~/.claude/sessions/<pid>.json` 이 있는 첫 프로세스를 찾는다.
  3. 그 파일의 `procStart` 가 그 프로세스의 생성 시각과 같은지 본다(pid 재사용 방지).
  4. `sessionId` 를 읽는다. transcript 경로 = `~/.claude/projects/*/<sessionId>.jsonl` 이다(프로젝트 폴더 수만큼 존재 확인).
  - 호출 때마다 다시 읽는다. `/clear` 뒤 바뀐 id 도 그대로 따라간다.
  - 비용: 단계 ≤ 4 + 프로젝트 폴더 수. 프로젝트 폴더 수는 이력 줄 수가 아니다. 그래도 자라는 항이라 KR2(무관)로 적는다. 다리가 「id → 경로」를 프로세스 안에 기억하면 같은 id 의 다음 호출은 1 이다.
- **vrs_restore 절차(데몬):**
  1. conv_tail(T) — 부른 시점의 파일 끝까지 넣는다.
  2. `vrs_wait_off(C(T), 그 끝)` — 처리된 앞부분이 그 끝을 덮을 때까지(M4, 상한 있음).
  3. 살아 있는 문맥 경계 b 를 정한다. T 끝에서 거꾸로 읽으며 처음 만나는 `compact_boundary` 줄의 위치다. 없으면 「압축 없음」이라 빈 결과다. 거꾸로 읽는 양은 살아 있는 문맥의 원본 바이트다. 모델 창 하나로 묶이고, N 과 무관하다.
  4. A = `vrs_assemble_b(C(T), budget)`.
  5. A 의 payload id `cc1:o:k` 가운데 o < b 이고 종류가 발화·assistant 답인 것을 고른다.
  6. 항목마다 원본 T 를 (o, n) 으로 읽고 sha256 = cc.h 를 확인한 뒤 블록 k 의 글을 꺼낸다.
  7. 쪽: 결과를 계보 위치(o, k) 순으로 늘어놓고, 상한 R 토큰(어림 = 바이트/4, 기본 20,000)까지 낸다. `next` 는 다음 항목의 (o, k) 다. `start` 를 받으면 그 위치부터 낸다.
  8. 첫 줄은 표지 「⟦vrs-restore v1 …⟧」다(C6, 자기 참조 제외 규칙의 열쇠).
  - 비용: 꼬리 + lib7 조립(일체화 T-int-8 쪽, 42f 실측 2.2 ms) + 결과 크기 + 살아 있는 문맥 바이트. N 이 없다.
- **vrs_read:** 루트(`~/.claude/projects`, auto-memory 폴더들) 아래 경로만 받는다. [start, end) 를 읽고 sha256 을 붙인다. R 을 넘으면 줄 경계까지 내고 `next` 를 준다. 비용은 읽는 범위다.
- **안내 훅:** SessionStart(`compact`) 에 `additionalContext` 한 문단(§11). 훅은 시험 설정에만 건다(M10).

### 14.6 변환기·데몬 세부 (L3 결정, 코드 전에 적음)
- **KF1 (L1 C2 꼴, 막음 — M2).** C2 는 payload id 를 `cc1:<o>:<k>` 로만 두었다. 그래서 조립 결과(payload 그대로, payload_of)에서 원본 줄의 길이 n 과 sha 를 알 수 없다. M2 의 sha 대조를 할 수 없다.
  - 고침: `cc` 객체를 맨 위가 아니라 **payload 안 마지막 칸**에 둔다. `"cc":{"o":<o>,"n":<n>,"k":"<k>","h":"<sha256 hex 64>"}` 이고, payload id 는 두지 않는다.
  - lib 이 읽는 칸과 겹치지 않는다. cc 에는 `"text"`·`"call_id"`·`"type"`·`"role"`·`"image_url"` 키가 없다. 그리고 `type`·`role` 은 payload 앞쪽(payload 시작 200자·줄 시작 400자 안)에 둔다.
  - 토큰 셈은 payload 바이트만큼 늘어난다. 현재 입력 쪽 셈이라 T-ks1 의 남는 차이(예산 경계)와 같은 부류다.
- 롤아웃 줄 꼴(바이트 그대로): `{"timestamp":"<ℓ 의 timestamp 원문>","ordinal":<10자리 0채움>,"type":"response_item"|"event_msg"|"session_meta","payload":{…,"cc":{…}}}` + `\n`.
  - 순번이 고정 폭이라 줄의 바이트 길이가 순번 값과 무관하다. 그래서 덩어리 병렬 변환에서 앞부분 합을 내기 전에 바이트 수를 안다.
- 첫 줄 session_meta: `{"timestamp":<θ_meta>,"ordinal":0000000000,"type":"session_meta","payload":{"id":"<T 의 파일 이름 줄기>"}}`. θ_meta = T 에서 (o 순으로) 출력 줄을 처음 내는 원본 줄의 timestamp 다. C(T) 는 그런 줄이 생길 때 처음 만든다.
- payload 꼴:
  - user(발화): `{"type":"message","role":"user","content":[{"type":"input_text","text":…}|{"type":"input_image","image_url":"data:<media_type>;base64,A"}],"cc":…}`
  - assistant: `{"type":"message","role":"assistant","content":[{"type":"output_text","text":…}],"cc":…}`
  - developer: `{"type":"message","role":"developer","content":[{"type":"input_text","text":"⟨cc⟩"}],"cc":…}`
  - function_call: `{"type":"function_call","name":…,"arguments":"{}","call_id":…,"cc":…}`
  - function_call_output: `{"type":"function_call_output","call_id":…,"output":"","cc":…}`
  - reasoning: `{"type":"reasoning","summary":[{"type":"summary_text","text":""}],"cc":…}`
  - task_started: `{"type":"task_started","turn_id":"<ℓ.uuid>","cc":…}`
  - task_complete: `{"type":"task_complete","last_agent_message":…|null,"cc":…}`
  - k 는 블록 번호(0부터, 문자열 content 는 0)다. 표지 줄은 `t`·`c`, 줄 하나에 하나인 것(isMeta·attachment·system local_command)은 `0` 이다.
- 사용자 줄의 처음 보는 블록 종류(document 등)는 0줄 + 셈이다(§7.0 (a) 의 일반 규칙).
- 요청 경로: 부른 스레드가 제 T 의 꼬리를 덩어리로 나누지 않고 스스로 변환한다(비용 = 꼬리). 큰 꼬리의 덩어리 병렬은 상주 일꾼의 일이다(첫 짓기·재기동).

### 14.13 KL1 고침 (2026-10-13 19시대, 사용자 「KL1 고쳐 ㄱㄱ」)

**원인(코드에서 찾음).** 데몬은 준비 판정을 `lib()!=null`(vrs_open 반환)로 한다. 이 판정은 `vrs_ccd.cpp:447`·`:498` 에 있다.
- lib7 은 열린 뒤에도 P-2 의 병렬 복원 동안 `S.ready==0` 이다(`vrs_lib.cpp:1222`).
- 이 사이에 요청이 오면 `vrs_wait` 가 `rd==1` 을 기다린다. 기다리는 시간은 timeout_ms=5000 이다(`vrs_lib.cpp:4225–4240`). 그 시간이 지나면 1 을 돌려주고, 데몬은 이것을 `VRS_WAIT_1` 로 낸다.

**정의(구현 자리의 뜻, KX1 그대로).**
- 준비 R ⟺ lib≠null ∧ vrs_ready(lib)=1.
- 요청이 왔을 때 갈래는 셋이다.
  - ¬R ∧ vrs_ready∈{0, lib 없음} 이면 곧바로 NOT_READY 를 낸다. 기다리지 않는다.
  - vrs_ready<0 이면 `VRS_READY_<rc>` 를 낸다. 저장소 실패를 이름으로 드러낸다.
  - R 이면 지금 길 그대로다.

**정리 KL1-T.** R 을 한 번 관측한 뒤 vrs_wait 가 1 을 돌려주는 경우는 「그 파일의 명시 삽입 접두가 공개되지 않음(pub<insert_end) 또는 계보 미설정」뿐이다.
- 증명.
  - ready 를 쓰는 자리는 셋이다. 0→1 CAS(`:3481`), 실패 때 -1 저장(`:3473`·`:3976`·`:4012`).
  - 0 으로 돌아가는 쓰기는 없다. 그러니 R 관측 뒤 vrs_wait 안에서 rd 는 1 또는 -1 이다.
  - rd=-1 이면 -2 를 돌려준다. rd=1 이면 파일 조건만 남는다. ∎
- 따라서 준비 뒤의 VRS_WAIT_1 은 진짜 「그 파일 공개 시간 초과」이고 이름이 뜻과 맞다.

- B 는 처음 훑기 집합 F₀ 의 원본 바이트 합이다.

**전제(근거 있음).**
- P-g1: lib7 의 먼 집합 N_far 는 「(y, 답) 내용 칸 승인」을 읽는다. 칸 배열은 전역이고, 칸의 셈은 계보와 상관없이 𝔅 의 모든 닫힌 턴에서 온다(§10.0: 「계보에 묶이지 않은 것: … 쌍 판정 J(x, y), 칸 배열(전역)」).
- P-g2: 승인은 셈의 문턱 함수다. 그래서 문턱 바로 아래에 있는 저장소에서는, 다른 세션의 턴 하나가 셈을 하나 올려 승인을 뒤집고, 그 결과 M(h) 가 바뀐다.
- P-g3: lib7 이 옛 이력을 순서 없이 받는 길은 열 때의 일괄 읽기(P-2) 하나다. 열린 lib 에 옛 턴을 넣으면 P-8 재셈 비용이 N 에 비례한다(§14.9 KX1 실측·정리). 그래서 변환을 다 한 뒤에 연다(T-kx1).
- P-g4: 요청을 붙잡아 기다리게 하지 않는다(KX1, 절대 규칙의 단계 대기 금지). 오류는 폴백 없이 드러낸다(§4 L1 끝 (c)). lib7 정의는 바꾸지 않는다(§1 Q1).

**정리 T-d1 (빈 data 의 첫 답 하한).** data 가 비어 있으면, A(s, 𝔅) 를 정확히 내는 어떤 절차든 T_R ≥ B / W 이다. W 는 원본을 읽는 대역폭의 상한이다.
- 증명.
  1. s 의 계보 밖에 있는 파일 f ∈ F₀ 의 줄 ℓ 하나를 잡는다.
  2. P-g1·P-g2 에 따라, ℓ 의 내용만 달라도 A(s, 𝔅) 가 달라지는 저장소가 있다.
  3. 그러니 ℓ 을 읽지 않고 A(s, 𝔅) 를 확정하는 절차는 그런 저장소에서 틀린다.
  4. 줄의 경계는 바이트를 읽어야 알 수 있으므로, ℓ 을 읽는다는 것은 f 를 ℓ 의 끝까지 읽는다는 뜻이다.
  5. 그래서 F₀ 의 모든 바이트를 한 번은 읽어야 하고, 읽기 시간은 B / W 이상이다. ∎
- 따름 T-d2. P-g4 아래에서 [0, T_R) 동안 정의된 답은 NOT_READY 하나뿐이다. 어댑터가 바꿀 수 있는 것은 상수(병렬 폭·변환 속도)뿐이고, 하한 B / W 는 남는다. B 는 이력과 함께 자란다(N 비례).
