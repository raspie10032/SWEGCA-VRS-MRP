# N-D: 할당과 빌드 (2026-10-13, nd)

## 정의 — L1 동결

`relay/tasks/RULES.md`와 `VRS_MCP_libvrs_v1.md` §13, §14.0–§14.10을 읽었다.
입력 바이트, VX06 해석/손상 판정, 턴/세션 정체, 항목/칸 판단과 조립은 lib7 그대로다.
N1은 끝의 `,"us":N`만 제외한 JSON 바이트, assemble rc 목록, cells_hash의 일치다.
이번 변경은 L2 저장 수명/용량과 L3 빌드다. A의 핸들/매핑/읽기 절차와 B의 게시/작업
분배는 고치지 않는다. N2 문턱(5초), N1 기대 출력, N4 금지 목록은 바꾸지 않는다.

## 수식 — 비용과 불변식

한 꼬리 읽기의 조각 상한 C=2^24 바이트, 미완성 줄의 잔여 길이를 R,
실제 읽힌 바이트 합을 T, 호출 횟수를 F라 한다. 기존 string의 resize는 읽기 전
매 조각의 C 바이트를 초기화한다. 짧은 꼬리도 C, EOF 확인에도 C를 쓰므로
초기화 비용은 Θ(C × 읽기 호출 수)다. 파일별 큰 할당/해제가 F번 반복된다.

대체 버퍼의 불변식은 `0 <= size <= capacity`, `[0,size)`만 초기화된 입력이다.
읽기 직전에는 reserve만 하고, 읽기 직후 성공한 got만 size에 더한다.
성장 때 복사하는 것은 이미 유효한 size 바이트뿐이다. 줄 소비 뒤에는 남은
R 바이트만 memmove한다. 스레드별 저장은 필요한 최대 크기까지 기하급수로
자라며, 다른 스레드의 저장과 공유하지 않는다. 비용은 읽기 Θ(T), 미완성 줄
보존 비용(기존과 같음), 성장시 유효 바이트 복사다. 저장소 크기 N 항은 없다.
스레드 종료시 메모리를 반환한다. 예외/중첩 호출은 호출별 임시 저장으로 분리한다.

레코드의 부분 수 np, 턴 view 길이 v가 이미 들어 있으므로 `reserve(np)`와
`reserve(v)`는 값/순서를 바꾸지 않고 기하급수 재할당을 최대 한 번으로 줄인다.
np는 남은 바이트/최소 부분 크기(14)로 검증한 뒤 예약한다. 손상된 길이로 큰
할당을 하지 않는다. 정체 해시는 마지막 경로 성분의 `.jsonl` 제거 후 끝 36바이트
FNV 또는 기존 상대 경로 FNV다. string_view로 같은 범위를 빌려 문자열 할당을 없앤다.

## 증명 — 저장 표현만 바뀐다

T-D1: 읽기 fd, 위치, 요청 길이 C, 순서, got 판정은 같다. 초기 유효 길이 0에서
시작해 이전 유효 바이트 + OS가 쓴 got 바이트를 이어 놓으므로 귀납적으로
파서가 관측하는 모든 바이트가 같다. EOF/오류시 길이는 늘지 않는다. reserve된
미초기화 영역은 find/memchr/insert_line에 전달하지 않는다. NUL/반쪽 줄 처리는 같다.

T-D2: 스레드 지역 버퍼 대여는 해당 스레드만 소유한다. 중첩 대여에는 별도의
호출별 버퍼를 준다. 반환시 유효 길이를 지우고 대여 표를 돌려놓는다. 새 잠금,
원자 순서열, 대기, 작업 주체, 스레드 생성은 없다. Windows는 기존 FLS 기반
VP_TLS를 써 emutls를 만들지 않고 Linux는 기존 방식의 thread_local을 쓴다.

T-D3: 부분과 view의 원소 수/값/순서는 바뀌지 않는다. 잘못된 np는 기존 파서도
최소 14바이트를 읽지 못하므로 동일하게 그 R_ITEM 하나를 손상으로 센다.
정체의 string_view 부분 범위는 기존 substr과 같아 FNV/seed가 같다.

## 알고리즘 — 코드 전에 고정

1. 재사용 바이트 버퍼/대여를 독립 헤더에 둔다. ingest_file_tail의 문자열 저장과
   읽기 전후 용량 처리만 바꾼다. A의 파일 I/O 코드는 그대로 둔다.
2. decode_record의 부분 벡터, validate_shard의 viidx 용량을 알려진 개수로 잡는다.
   fid_key는 빌린 문자열 범위로 같은 해시를 구한다.
3. 빌드는 실제 native/libvrs와 src 경로를 사용하고 릴레이와 같은 소스 집합,
   O2/C++20/ffp-contract=off/64비트 offset/Windows 8 설정을 쓴다.
   mimalloc 2.1.7 static.c와 new/delete 대체 목적 파일을 모든 실행 파일에 직접
   링크한다. Linux에도 같은 할당기를 정적으로 링크하되 OS 런타임 전체의 정적
   링크는 강제하지 않는다. 모든 Linux 빌드/시험은 CPU 0–11이다.
4. N4 검사에는 native/libvrs와 src의 직접 cpp/h/hpp, 빌드된 제품 목적 파일을
   포함한다. mimalloc의 두 목적 파일은 릴레이와 같이 별도 의존성으로 분리하고
   제외 사실을 출력한다. nm 실패/목적 파일 누락은 실패다. Linux 기존 atomic
   wait의 심볼은 Windows 조건과 별도로 보고한다. 링크된 mimalloc 확인도 한다.
5. reopen 도구는 준비 시점의 OS 페이지 폴트/메모리와 close 뒤 mimalloc 통계를
   보고한다. 측정은 판단에 쓰이지 않는다. 고정 릴레이가 원문을 버리는 제한은
   보고하고 원문 보존을 요청한다. 시험 기대값에 통계를 끼워 넣지 않는다.

## 검증 계획과 발견한 결함

- D-ALLOC (L2, 늦춤; KX3/M8의 원인 후보): 16 MiB 0채움/파일별 할당. 동일
  mimalloc 빌드에서 main과 수정판의 재열기 1/6 일꾼을 측정한다. 측정 전 원인
  후보이며 Windows 페이지 폴트 감소를 아직 확인한 것은 아니다.
- D-BUILD (L3, 막음): 기존 src/build.sh/build_windows.ps1이 없는 ref/를 사용하고
  mimalloc 정적 링크가 없다. 실제 소스와 릴레이 레시피로 고친다.
- D-RELAY (시험 계측, 막음 — N1 판정): 기존 main `base-smoke2`가 cells_hash와
  JSON은 같지만 rc_list_equal=false다. 기준/정규식을 임의 수정하지 않고 원문
  근거를 확인한다. frozen SHA256=3ca3e5a4db1e450a8bcc4db38df63360a06584d6e89dd5edb852628137f12aa8.
- Linux: m1(409), kx2(1206)의 batch/reopen 모두 frozen 기준과 비교한다.
- Windows: static, n1_m1, n1_kx2, reopen을 요청한다. 기준 main은 동일 정적
  mimalloc `base-smoke2`의 reopen 3014.5/3024.3/3057.7 ms다.
- raw buffer는 실제 파일 읽기/NUL/반쪽 줄/큰 줄/중첩 수명 검사를 하고 기존
  insert replay/ooo 시험도 실행한다. 새 대기 자리는 0개다.

## 범위와 통합 경계

변경은 nd 작업 트리에만 한다(사용자가 지정한 보고서/중계 요청은 별도).
lib7의 기존 작업 구조와 일반 할당기 내부 동기화는 D가 재설계하지 않는다.
새 버퍼는 기존 FLS 정리로 반환한다. A와 겹칠 수 있는 ingest_file_tail에서는
버퍼 선언과 reserve/read-result 부분만 D 변경이다. N2/N3/N5 전체 통합은 E 범위다.
